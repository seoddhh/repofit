# 소개 재사용과 누락 해설 보충

2026-11-02 KST 검토. 아래 구현과 21개 원고는 로컬 준비본이며 아직 운영에 배포하거나 게시하지 않았다.

## 확인한 운영 상태

RepoFit 공개 읽기 API로 오늘 17개, 이번 주 16개, 이번 달 19개를 확인했다. 중복 제거 후 43개 중 기존 해설은 22개, 없는 해설은 21개였다. 각 조회 결과와 원문은 버전 관리에서 제외한 `outputs/`에 보관했다. 운영 큐는 기존 글의 자료 재확인까지 수행해 39개의 한도 오류를 반환했다. 이는 빈 글 39개를 뜻하지 않는다.

기존 구현도 일반 코드 커밋 자체를 비교하지는 않았다. README 본문과 SHA, 릴리스 및 설명 등을 매번 다시 가져와 비교했다. 따라서 코드 변경만으로 무조건 글을 재작성한다는 진단은 정확하지 않다. 문제는 소개가 이미 있어도 자료 확인에 REST 호출이 들고, 작은 README 편집과 새 릴리스가 소개 전체의 재작성 조건이 된다는 점이다.

비인증 GitHub REST API의 기본 한도는 IP당 시간당 60회다. 현재 수집기는 저장소당 메타데이터, README, 릴리스 등 최대 3회를 사용하므로 43개 최초 수집에는 약 129회가 필요하다. 3개씩 작성하더라도 기존 저장소를 계속 재확인하면 전체 비용은 줄지 않는다. [GitHub 공식 한도 문서](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

## 판단과 운영 기준

서비스의 핵심이 ‘어떤 도구이며 어디에 쓰는가’라면 커밋과 릴리스마다 소개 전체를 재생성할 필요가 없다. 재작성은 비용뿐 아니라 사실 오류와 표현 흔들림도 만들 수 있다. 반대로 영구 불변으로 취급하면 도구의 목적 변경, 서비스 종료, 라이선스나 핵심 설치 경로 변경을 놓칠 수 있다.

따라서 다음을 구분한다.

| 정보 | 기준 |
| --- | --- |
| 현재 트렌딩 목록, 순위 및 스타 | 기존처럼 기간별 최신 목록을 수집한다. |
| 도구의 목적, 주요 용도와 기본 사용 흐름 | 한 번 작성한 해설을 기간과 재등장에 관계없이 재사용한다. 자동 큐는 해설이 없는 저장소만 수집한다. |
| README 수정, 코드 커밋, 단순 버그 수정 릴리스 | 소개 전체의 자동 재작성 조건으로 사용하지 않는다. |
| 목적과 주요 기능의 변경, 라이선스 변경, 프로젝트 종료, 핵심 설치 절차 변경, 독자의 오류 제보 | 영향을 받는 부분을 별도 편집 대상으로 검토한다. 이번 작업에서 정기 재검토 예약이나 자동 감시 기능을 추가하지 않는다. |
| ‘왜 지금 주목받는가’ 및 확인한 릴리스 | 당시 관측과 근거로 읽는다. 미래의 인기 원인이나 최신 릴리스라고 주장하지 않는다. |

GitHub의 `weekly`와 `monthly` 페이지는 현재 목록이다. RepoFit도 5분 캐시로 이를 수집하므로 ‘주 1회/월 1회 수집한 고정 목록’이 아니다. 한 주나 한 달이 끝난 뒤 별도 저장한 스냅샷이라면 고정 기록으로 둘 수 있지만, 이번에는 목록을 고정하지 않는다. 같은 저장소의 소개 재사용은 목록 고정과 별개다.

## 준비한 구현

- `get_editorial_queue({})`는 세 기간 합집합에서 기존 해설이 있는 항목을 외부 호출 전에 제외한다. `changeDetection`은 `missing-only-v1`, `dueRepositories`는 실제로 해설이 없는 수다. `unchangedRepositories` 및 `freshRepositories`는 호환용 기존 해설 수이며 최근 원문을 재검증했다는 뜻은 아니다.
- 한 번에 최대 3개를 **시도**한다. 실패도 횟수에 포함하고 429 한도 오류는 첫 발생에 중단한다. README나 릴리스 단계에서 난 429도 삼키지 않는다. 한도 오류를 없애는 기능은 아니며 새 저장소 최초 수집에는 여전히 호출 예산이 필요하다.
- `import_repository_brief`는 소유자가 직접 확인한 공식 README와 해설을 한 번에 등록한다. 최근 하루 안의 확인 시각, 해당 저장소의 공식 URL과 게시 형식을 검사한다. 기존 글을 교체하지 않고 동시 실행과 재시도도 기존 본문 및 시각을 보존한다. 방문자나 다른 계정은 호출할 수 없다. 외부 REST API 호출 없이 기존 Trending HTML 수집 경로만 사용한다.
- 해설 작성 후 36시간이 지났다는 이유만으로 지연 경고를 띄우지 않는다. 별도로 저장된 더 새로운 자료와 실제 차이가 있을 때만 차이를 표시한다. 이는 최신성 보증이 아니라 작성 시점의 소개이며 출처 확인 시각을 계속 표시한다.
- DB 스키마 및 예약 일정과 설정은 변경하지 않았다. 현행 예약은 2026-11-02 조회에서 매일 09:17 Asia/Seoul, 활성 상태였다. 과거 문서의 일시중지 기록은 당시 상태다.

## 준비한 콘텐츠와 검증

[21개 해설 원고](../content/editorial/2026-11-02-missing.md)와 [공식 출처 및 등록 데이터](../content/editorial/2026-11-02-missing.json)를 준비했다. 각 공식 저장소 페이지와 README를 직접 읽었다. 긴 원문은 연구용 `outputs/`에만 두고 등록 데이터에는 저장소별 25단어 이하의 확인한 발췌만 넣었다. 라이선스 식별자를 별도로 확인하지 않은 항목은 null과 경고로 표시했다. 관심의 직접 원인은 확인되지 않았다고 명시했으며 설치와 실행은 수행하지 않았다.

현재 운영 도구에는 수동 수집 자료 등록 경로가 없다. 따라서 직접 수집한 원고를 운영에 반영하려면 이 변경을 배포한 뒤 소유자 도구로 등록하고, 21개 글의 본문과 출처 및 작성 시각을 재조회해야 한다. 로컬 원고나 코드 검증을 운영 게시 완료로 보고하지 않는다.
