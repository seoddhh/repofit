# 공개 GitHub 오픈소스 스냅샷

사용자 요청은 저장된 자료만 읽는다. GitHub 수집은 소유자 전용 예약 작업으로 분리한다. 한국 시간 매일 00:00, 08:00, 16:00에 오늘·이번 주·이번 달 목록과 중복 제거한 공개 레포의 상세 자료를 갱신한다. 통합 예약 하나가 하루 세 번 목록 수집 → 신규 레포 자료 수집 → 신규 한국어 해설 작성 → 완성 스냅샷 공개를 수행한다. 기존 매일 09:17 해설 예약은 비활성 상태로 유지하며 사용하지 않는다. 스킬 카탈로그 예약은 별도다.

## 저장과 공개

- `repository_snapshot_state`: 작업 진행 위치와 lease, 완료된 버전별 manifest, 현재 `active` manifest를 보관한다.
- `repository_snapshot_items`: 버전과 저장소 이름으로 목록에 포함된 레포의 소개·라이선스·README·릴리스·커밋·의존성·제한된 파일 경로를 보관한다.
- 수집 요청 한 번에 레포 하나를 처리한다. 성공한 위치를 DB에 저장해 다음 요청에서 이어간다. 같은 레포가 여러 기간에 있어도 한 번만 수집한다.
- 세 기간의 트렌딩 목록과 순위는 갱신마다 수집한다. 이미 자료가 있는 레포는 GitHub API를 다시 호출하지 않고 README·릴리스·파일 구조·의존성·소개·라이선스 등 저장 자료를 그대로 재사용한다. 신규 레포만 상세 자료를 수집한다.
- `repository_materials`는 레포별 자료를 영구 보관하며 스냅샷 보관 기간과 무관하다. 마이그레이션 0010은 기존 스냅샷 자료를 이관한다. 스냅샷 이전에 작성한 해설만 있는 레포도 저장된 근거를 재사용하며, 수집하지 않은 파일 구조와 커밋을 만들어내지 않는다. 기존 한국어 해설과 원래 근거·작성 시각은 변경하지 않는다.
- DB lease로 다른 Worker에서도 동시 수집을 막는다. lease가 만료된 이전 실행은 항목과 공개 포인터를 쓰지 못한다.
- 모든 항목의 자료 수집과 신규 해설 저장을 확인한 뒤 manifest와 `active`를 D1 batch로 공개한다. 자료 수집만 끝난 버전은 `working`에 남고 공개 목록 및 버전 주소로 읽을 수 없다. 실패하면 이전 정상 버전을 그대로 보여준다. 첫 예약 전과 최초 수집 중에는 기존 운영 API에서 보존한 `content/repository-snapshot-baseline.json`의 세 기간 목록과 기존 저장 해설을 제공한다. 방문자 요청에서 수집하지 않으며 첫 수집 완료 후에만 새 목록으로 교체한다.
- 같은 한국 시간 8시간 구간에서 완료된 버전은 다시 수집하지 않는다. 수집 실패는 다음 호출에서 재시도할 수 있다. 새 시간 구간에는 새 목록으로 시작한다.
- 오래된 버전은 최소 2일간 유지하고 현재 및 직전 공개 버전은 정리 대상에서 제외한다. 정리는 공개 갱신 때만 수행하며 사용자 조회에서 하지 않는다.

## 공개 읽기

- `GET /api/trending?since=daily|weekly|monthly`: active 목록, snapshotId, 수집 시각, 다음 갱신 시각을 반환한다.
- `GET /api/brief?repository=owner/repo&snapshot=<UUID>&since=weekly`: 목록과 같은 버전·같은 기간의 수치와 저장된 해설을 읽는다. snapshot을 생략하면 active를 읽는다.
- `POST /api/repository`: 저장된 active 상세만 반환한다. 임의 레포를 입력해도 GitHub를 호출하지 않으며 미수집 레포는 404다. 개인 프로젝트를 사용자 GitHub 연결로 가져오는 기능은 별도 범위다.
- 목록과 해설 API에는 60초 공개 캐시를 사용한다. 브라우저의 새로고침은 저장된 최신 버전을 다시 읽는 동작이다.
- 다음 갱신 예정 시각에서 30분이 지나도 새 버전이 없으면 이전 자료임을 표시한다. 기존 한국어 해설의 원래 근거와 작성 시각은 보존하고, 수치·공식 자료는 해당 스냅샷을 사용한다.

## 예약 작업 계약

연결된 RepoFit MCP의 `refresh_repository_snapshot`을 빈 객체로 호출한다. `phase: collecting`이면 같은 도구를 반복한다. `phase: editorial`이면 `get_editorial_queue`를 빈 객체로 호출하여 신규 해설만 작성·저장한다. `dueRepositories: 0`이 되면 `refresh_repository_snapshot`을 다시 호출해 완성 스냅샷을 공개한다. `published: true`이면 `get_repository_snapshot_status`로 ready, version, 기간별 개수와 마지막 수집 시각을 확인한다. busy, 오류, 진행 정체가 있으면 반복하지 말고 실패를 보고한다. 사용자 원문·로컬 파일·브라우저 로그인·공용 토큰 직접 입력은 필요 없다. GitHub 토큰은 Sites 런타임 비밀값을 이용하며 private 저장소 응답은 거부한다.

예약은 데이터만 갱신한다. Git 수정·커밋·배포·권한 변경은 하지 않는다. 통합 예약이 `get_editorial_queue`로 비공개 준비 스냅샷의 신규 레포만 작성한다. 기존 해설은 fingerprint가 달라도 덮어쓰지 않는다. 실패하면 공개 포인터는 이전 완성 스냅샷에 남는다. 실행 지침은 [통합 예약 지침](EDITORIAL_SCHEDULE_PROMPT.md)에 보관한다.

## 검증

`node scripts/verify-repository-snapshots.mjs`는 한국 시간 경계, 재개, lease, 원자적 공개, 오류·private 응답 시 이전 버전 유지, 과거 버전 일치, 공개 요청 100회에서 외부 호출 0회를 확인한다. `verify-briefs.mjs`는 해설 큐도 외부 조회 없이 스냅샷을 사용하고 기존 해설의 작성 시점·근거를 보존함을 확인한다. 새 테이블은 0009 마이그레이션으로 추가하며 기존 보고서 테이블은 변경하지 않는다.

`node scripts/verify-incremental-snapshots.mjs`는 기존 레포 API 호출 0회, 신규 레포만 수집, 목록에서 사라졌다가 다시 등장한 레포 자료 재사용, 스냅샷 정리 후 자료 유지, 기존 해설 작성 시각 보존과 해설 완료 전 공개 차단을 확인한다.
